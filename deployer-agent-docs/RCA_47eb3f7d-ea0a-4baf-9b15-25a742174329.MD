## User report
"On the daily report of 10/20 I added a delay with 9 days impact; the schedule didn't slip a single day, and the delay did not show on the 10/29 daily report."

## Verdict
**Working as designed — the delay consumed float only.** The delay WAS linked to a task, the impact WAS recorded, and the engine correctly chose not to slip the schedule because the linked task had far more float than the impact. This is NOT a "not-linked" problem and NOT a "CPM-didn't-recompute" problem. Two secondary observations (a backdated/absent report date, and a 9-vs-8 day number mismatch) explain the rest of the confusion.

## Root cause (answer to the three hypotheses)
1. **Float-only consumption — CONFIRMED.** Impact (8 days) < task float (23 days) and the task is not on the critical path → `consumes_float_only=true`, `pushes_critical_path=false`. The schedule correctly did not slip. The project finish date is unchanged (2027-12-28). This is the designed behavior of the impact_days engine.
2. **Not-linked — RULED OUT.** The delay links to task VA6B-1680; linked_task_ids is populated and the task shows `last_synced_from_dr` confirmed.
3. **CPM didn't recompute — N/A / RULED OUT.** The project uses the impact_days engine, not CPM; impact was computed and stored per task at logging. No CPM artifacts are expected or missing.

## Secondary observations
- **"10/29 daily report" does not exist.** The only daily report for this project is report_date 2026-10-20 (authored 10/29). If the user opened the 10/29 date in the UI, it is empty simply because no report was ever created for 10/29 — the delay lives on the 10/20 report. Nothing is lost.
- **9 vs 8 day mismatch.** User recalls "9 days impact" but the stored projected_impact_days is 8 (delay_days top-level field is null). Even at 9 the outcome is identical (9 < 23 → still float-only). Worth confirming what the user entered vs what was saved.
- **Task float not decremented.** After an 8-day float-only consumption, the task still shows total_float_days = 23 AND remaining_float_days = 23 (and remaining_float_at_logging_days = 23). If the product intends consumed float to reduce a task's remaining float going forward, this would be a code/engine gap — flag for review. If impacts are meant to be tracked separately and netted elsewhere, this is expected.

## Suggested fixes
- **User (understanding/decision):** Behavior is correct. For the schedule to slip, the impact must exceed the linked task's available float (here 23 days) or be linked to a critical-path task. The delay is on the 10/20 report, not a 10/29 report. Confirm whether you meant 8 or 9 days.
- **Code (E1, only if product intent differs):** (a) Decide whether float-only consumption should decrement the task's remaining_float_days (currently stays at 23). (b) Consider surfacing float-only delays more visibly on the report/schedule view so users see "absorbed by float, no slip" rather than appearing as if nothing happened.
